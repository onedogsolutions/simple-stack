The provider layer is rooted at `CLOUD_PROVIDER_API` (`class-cloud-provider-api.php`), which defines the shared contract: provider identity (`_PROVIDER`, `_PROVIDER_SLUG`), feature flags (`snapshots`, `resize`, `ssh_create`, `test_connection`, …), normalized server states, credential helpers, and WordPress transient caching keyed by provider/site/version plus a SHA-256 credential fingerprint and API method. The Simple Stack bootstrap registers exactly two concrete providers:
- `CLOUD_PROVIDER_API_VultrV2` extends the base class directly and targets `https://api.vultr.com/v2/` with bearer-token authentication. It supports connection tests, SSH-key creation, resize, snapshots and backups; custom images and dynamic tags remain disabled.
- `CLOUD_PROVIDER_API_Upcloud` also extends the base class directly and targets `https://api.upcloud.com/1.3/` with HTTP Basic authentication using an account user name and password. It supports connection tests, SSH-key creation and resize; snapshot and backup flags stay off because UpCloud's storage-backup model does not fit the snapshot-id contract.

Both providers may be instantiated under virtual aliases backed by the `sstk_cloud_provider` post type, while their base provider identity remains fixed. Each registers its dashboard link, feature flags and `sstk_cloud_provider_settings_*` filters for the Simple Stack admin UI. Outbound calls use `wp_remote_request`, failures return `WP_Error`, credentials are decrypted only in memory, and request headers, bodies and full credential-bearing URLs are never logged.
