Three sibling base classes form the foundation of the app/provider layer:
- `SSTK_APP` (class-sstk-app.php) extends `SSTK_Base` and is the abstract parent for concrete apps (e.g. WordPress). It wires admin hooks (`post_row_actions`, `admin_enqueue_scripts`, `rwmb_meta_boxes`, `save_post`), registers a public REST callback route at `{app_name}/v{SSTK_REST_VERSION}/command/{id}/{name}/{status}/{cmdid}/`, manages per-app temp script storage under `wp-content/uploads/sstk_app_{app_name}/scripts/`, resolves the active provisioning-script version via `get_configured_scripts_version()` (defaulting to `v2` with backward-compat fallbacks), and exposes token replacement helpers (`replace_script_tokens`, `add_custom_field_tokens_to_script`). It also provides Simple Stack-specific hardening: `get_sstk_admin_ip()` validates IPv4/IPv6/CIDR before interpolation into Bash, and `get_post_site_install_plugins()` filters/sanitizes plugin slugs for the `sstk_post_site_install` hook.
- `SSTK_APP_SETTINGS` (class-sstk-app-settings.php) is an empty placeholder parent class for per-app settings subclasses — a stable extension point without behaviour.
- `SSTK_SSH` (class-sstk-ssh.php) wraps phpseclib3 (`SSH2`, `SFTP`, `PublicKeyLoader`, `EC`) to execute remote commands, upload/download files, and generate Ed25519 keypairs. It centralises login failure, timeout negotiation (callback vs. long-running), result logging via `SSTK_POSTS_SSH_LOG()`, and user-name overrides through `sstk_exec_ssh_user` / `sstk_download_ssh_user` / `sstk_upload_ssh_user` filters.

Dependency direction inside the module: `SSTK_SSH` depends only on phpseclib3 and global SSTK helpers; `SSTK_APP` depends on `SSTK_SSH` indirectly (via child apps) and on `SSTK()` for providers and option access; neither file requires the other directly. Concrete app classes extend `SSTK_APP` and override `add_app()` plus any metabox/script logic.
