Two flat sub-directories with no build step:
- `assets/css/` holds four hand-written stylesheets scoped to the WordPress App screens (`sstk-wpapp-admin-app.css`, `sstk-wpapp-frontend.css`, `sstk-public-common.css`, `sstk-wpapp-update-plans.css`).
- `assets/js/` contains jQuery-driven scripts loaded only on specific wp-admin screens; each file is self-contained and declares its globals via `/* global ajaxurl */` / `/* global params */` comments. The entry point for the app-edit screen is `sstk-wpapp-admin-app.js`; shared behavior across both SERVERS and APPS screens lives in `sstk-wpapp-admin-common.js`, which centralizes the action dispatch pattern (click → FormData POST to `ajaxurl` with `_action` + `nonce` + `id`) and handles success branches: redirect, refresh, async polling, file download, and email-field autofill.
- `templates/` mixes `.php` view files (loaded via `require`/`include` from the parent app class) and raw HTML fragments (`email-admin.html`, `front-end-help-popup.html`). PHP templates are rendered into wp-admin metaboxes or modal popups and rely on the parent app class's `$this->get_app_name()` to scope dynamic `do_action("sstk_{$this->get_app_name()}_...")` hooks around every major section (header/title/form/console/install button), enabling child apps to inject fields without editing these templates.
Dependency direction is one-way: templates depend on data passed by the parent app class; JS depends only on `ajaxurl`, `params`, and jQuery — it never imports other modules. There is no asset pipeline, bundler, or CSS framework beyond plain CSS variables (`--sstk-*` tokens).
