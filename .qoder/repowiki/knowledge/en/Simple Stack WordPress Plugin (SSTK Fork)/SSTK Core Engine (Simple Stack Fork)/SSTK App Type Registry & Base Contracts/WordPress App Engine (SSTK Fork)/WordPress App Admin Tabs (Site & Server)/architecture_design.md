Two parallel sub-directories mirror each other: `tabs/` holds site-detail tab classes (one file per tab) and `tabs-server/` holds server-detail tab classes. Both extend the base class `SSTK_WORDPRESS_TABS` defined in `tabs/tabs.php`, which provides shared helpers (`get_fields_for_tab`, `submit_generic_server_command`, disabled/max-sites headers) and the field-to-action mapping contract.

Each tab file declares a class named `SSTK_WORDPRESS_TABS_<NAME>` (site) or `SSTK_WORDPRESS_TABS_SERVER_<NAME>` (server) whose constructor registers three filters on app-name-scoped hooks:
- `sstk_app_{$app}_get_tabnames` / `sstk_server_{$app}_get_tabnames` — register the tab slug + label + icon.
- `sstk_app_{$app}_get_tabs` / `sstk_server_{$app}_get_tabs` — return the metabox.io field array via `get_actions()`.
- `sstk_app_{$app}_tab_action` / `sstk_server_{$app}_tab_action` — dispatch the action string through a switch/case.

The `tabs-server/callbacks.php` file additionally wires background-task hooks (`sstk_pending_log_*`, `run_server_callbacks`) and bulk-action hooks on the server list screen, chaining two SSH scripts (`server_status_callback.txt`, `server_restart_callback.txt`) and publishing success/failure events under `sstk_server_wordpress-app_server_status_callback_*`. Remote work is always funneled through `$this->execute_ssh('generic', $instance, ...)` and `$this->turn_script_into_command(...)`; there are no direct shell calls from these files. The `tabs-server/general.php` entry point is intentionally a placeholder (marked NOT USED HERE / PLACEHOLDER ONLY) and only injects top-of-metabox summary columns via `get_nontab_fields`.
