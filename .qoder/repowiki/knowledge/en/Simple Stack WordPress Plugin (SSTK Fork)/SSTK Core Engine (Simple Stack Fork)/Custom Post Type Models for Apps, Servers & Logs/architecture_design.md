Two parallel hierarchies live side-by-side under this scope:

- Business CPTs: `SSTK_Posts_Base` is a thin base providing shared admin UI helpers (`display_post_states`, label rendering). `SSTK_POSTS_APP` and `SSTK_POSTS_APP_SERVER` extend it, each registering one CPT (`sstk_app`, `sstk_app_server`) plus a group taxonomy (`sstk_app_group`, `sstk_app_server_group`). They share cross-cutting behaviour via traits — `sstk_get_set_post_type`, `sstk_metaboxes_for_taxonomies_for_servers_and_apps`, `sstk_metaboxes_for_teams_for_servers_and_apps`, `sstk_metaboxes_for_labels_notes_for_servers_and_apps` — so server and app screens stay in sync.
- Log CPTs: `SSTK_POSTS_LOG` extends `SSTK_Posts_Base` and adds generic log-list UI (purge AJAX, search across configured meta fields, auto-trim by per-log limit, back-to-list button, capability gate `sstk_manage_logs`). Concrete logs (`SSTK_COMMAND_LOG`, `SSTK_ERROR_LOG`, `SSTK_SSH_LOG`, `SSTK_NOTIFY_LOG`, `SSTK_NOTIFY_SENT_LOG`, `SSTK_PENDING_TASKS_LOG`, `SSTK_APP_UPDATE_LOG` implied) extend it, set their own `post_type` and `post_search_fields`, and register their own columns/meta boxes.
- Non-CPT models: `SSTK_POSTS_TEAM` and `SSTK_POSTS_PERMISSION_TYPE` are standalone singletons that register their own CPTs (`sstk_team`, `sstk_permission_type`) with dedicated capabilities (`sstk_manage_teams`, `sstk_manage_permissions`).

Dependency direction is strictly downward: concrete classes depend on the two bases; bases do not know about concrete subclasses. All WordPress hooks (`add_action`/`add_filter`) are registered inside each class's constructor → `register()` → `hooks()` pipeline, keeping per-CPT bootstrap self-contained.
