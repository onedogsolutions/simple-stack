Two parallel sub-directories mirror each other: `tabs/` defines site-level admin tabs (e.g. general, backup, ssl, sftp, staging) while `tabs-server/` defines server-level tabs (e.g. services, power, resize, ssh_console, fail2ban). Both share a single base class `WPCD_WORDPRESS_TABS` in `tabs/tabs.php`, which extends `WPCD_WORDPRESS_APP` and provides common helpers (`get_fields_for_tab`, `submit_generic_server_command`, `get_disabled_header_field`, `get_max_sites_exceeded_header_field`). Each tab file declares one class extending this base and registers itself via three WordPress filters — `wpcd_app_{$app}_get_tabnames`, `wpcd_app_{$app}_get_tabs`, and `wpcd_app_{$app}_tab_action` (or the `wpcd_server_*` variants for server tabs) — so the parent app class discovers and renders them dynamically. Tab classes implement a fixed contract: `get_tab_slug()`, `get_view_tab_team_permission_slug()`, `get_tab($tabs,$id)` to register the tab entry, `get_tab_fields($fields,$id)` to return metabox.io field arrays, `tab_action($result,$action,$id)` to handle AJAX submissions, and `get_actions($id)` to supply the declarative action list consumed by `get_fields_for_tab`. Long-running or destructive operations are dispatched through `execute_ssh()` / `turn_script_into_command()` against remote bash scripts, with success/failure propagated via `WP_Error` objects and backgrounded through the pending-tasks log (`WPCD_POSTS_PENDING_TASKS_LOG`) when needed.
