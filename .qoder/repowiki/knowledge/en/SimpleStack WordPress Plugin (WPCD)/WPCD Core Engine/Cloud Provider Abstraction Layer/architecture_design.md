Three-tier class hierarchy rooted at `CLOUD_PROVIDER_API` (`class-cloud-provider-api.php`), which defines the shared contract: provider identity (`_PROVIDER`, `_PROVIDER_SLUG`), feature flags (`snapshots`, `resize`, `ssh_create`, `test_connection`, …), state constants (`_STATE_NEW/_ACTIVE/_OFF/_ERRORED/_INPROGRESS/_UNKNOWN`), credential helpers (`get_api_key`/`get_secret_key`/`uses_api_key`/`has_credentials`), and a WordPress transient-based cache keyed by provider slug + decrypted secret hash. Two parallel branches extend it:
- DigitalOcean branch: `CLOUD_PROVIDER_API_DigitalOcean_Parent` implements the full `call()` dispatch over `wp_remote_request` to `https://api.digitalocean.com/v2/` with Bearer-token auth; `CLOUD_PROVIDER_API_DigitalOcean` is a thin subclass that only overrides constructor defaults.
- Generic branch: `CLOUD_PROVIDER_API_CustomServer_Parent` provides a mock provider backed by static IPv4/IPv6 addresses and manual settings, used as the base for `CLOUD_PROVIDER_API_CustomServer`.

Concrete leaf providers `CLOUD_PROVIDER_API_Upcloud` and `CLOUD_PROVIDER_API_VultrV2` extend `CLOUD_PROVIDER_API` directly (not through the DO parent) because their authentication differs — UpCloud uses HTTP Basic with username/password (`uses_api_key() = false`) while Vultr uses bearer tokens like DigitalOcean. Each leaf registers its own dashboard link, feature flags, and `wpcd_cloud_provider_settings_*` filters to inject provider-specific settings fields into the WPCD admin UI. All outbound requests go through `wp_remote_request`; credentials are read via `WPCD()->decrypt(wpcd_get_early_option(...))` and never logged in request bodies or headers.
