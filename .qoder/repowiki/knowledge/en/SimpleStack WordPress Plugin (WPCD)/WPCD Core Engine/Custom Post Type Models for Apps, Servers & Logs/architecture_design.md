Two parallel hierarchies live side-by-side under this scope:

- Business CPTs: `WPCD_Posts_Base` is a thin base providing shared admin UI helpers (`display_post_states`, label rendering). `WPCD_POSTS_APP` and `WPCD_POSTS_APP_SERVER` extend it, each registering one CPT (`wpcd_app`, `wpcd_app_server`) plus a group taxonomy (`wpcd_app_group`, `wpcd_app_server_group`). They share cross-cutting behaviour via traits — `wpcd_get_set_post_type`, `wpcd_metaboxes_for_taxonomies_for_servers_and_apps`, `wpcd_metaboxes_for_teams_for_servers_and_apps`, `wpcd_metaboxes_for_labels_notes_for_servers_and_apps` — so server and app screens stay in sync.
- Log CPTs: `WPCD_POSTS_LOG` extends `WPCD_Posts_Base` and adds generic log-list UI (purge AJAX, search across configured meta fields, auto-trim by per-log limit, back-to-list button, capability gate `wpcd_manage_logs`). Concrete logs (`WPCD_COMMAND_LOG`, `WPCD_ERROR_LOG`, `WPCD_SSH_LOG`, `WPCD_NOTIFY_LOG`, `WPCD_NOTIFY_SENT_LOG`, `WPCD_PENDING_TASKS_LOG`, `WPCD_APP_UPDATE_LOG` implied) extend it, set their own `post_type` and `post_search_fields`, and register their own columns/meta boxes.
- Non-CPT models: `WPCD_POSTS_TEAM` and `WPCD_POSTS_PERMISSION_TYPE` are standalone singletons that register their own CPTs (`wpcd_team`, `wpcd_permission_type`) with dedicated capabilities (`wpcd_manage_teams`, `wpcd_manage_permissions`).

Dependency direction is strictly downward: concrete classes depend on the two bases; bases do not know about concrete subclasses. All WordPress hooks (`add_action`/`add_filter`) are registered inside each class's constructor → `register()` → `hooks()` pipeline, keeping per-CPT bootstrap self-contained.
